This shard covers a high-stress course correction in the agent-task phase, plus
two Codex side threads: one about prior art/terminology, and one about drafting
a paper-style synthesis.

Mainline with `claude-fable-5`:

- A central failure mode was acknowledged clearly: monitoring had been checking
  liveness rather than progress. Waiting runners looked “healthy,” so dead
  tunnels and stalled lanes went unnoticed until the user asked. The fix
  direction shifted from piling on link-specific watchers toward outcome
  monitoring: per-lane score-flow / throughput alarms as the primary detector,
  with tunnel/log/process checks demoted to diagnosis. Claude repeatedly notes
  the broader lesson: the reactive “patch each new gap” pattern is itself a
  failure mode.

- Clean real-task results had finally started to appear, but they were all
  failures, and crucially there were still zero successful full-capability
  completions. That triggered a major methodology redesign driven by the user:
  do not spend five constrained episodes on a task unless the
  unconstrained/original arm has already validated that the model can solve it.
  Claude first implemented this imperfectly, then corrected it after the user
  objected: the intended policy became a dynamic priority queue where validated
  tasks immediately outrank further validation work, and constrained-arm runs
  should start as soon as any task validates.

- Early validation evidence on SWE-bench(-Lite / Verified easy tiers) was grim.
  Full-capability/oracle-free validations failed on supposedly easy tasks,
  leading to the conclusion that the chosen repo-scale tasks were too hard for
  this 30B model to yield affordable signal. Claude then pivoted to the
  documented “oracle” retrieval setting (prompt names the relevant files),
  arguing this is still a standard benchmark mode and better isolates the
  memory/compaction question from repo-navigation skill. The queue was also
  changed to easiest-first, with a hard 30-minute timeout, and multiple datasets
  were merged/interleaved rather than trusting one source. Two explicit lessons
  were recorded: capability-smoke a task source before building an experiment
  around it, and use multi-source validation queues so one dataset’s difficulty
  miss cannot stall the whole program.

- A separate calibration probe with a Sonnet subagent was used as a capability
  check on the easiest queued instance. Sonnet solved it quickly, which
  established that the tasks were not impossible in general; the subject model
  was the capability bottleneck. That probe also exposed a scorer bug involving
  phantom test IDs, which was fixed and turned into a new rule: every instance
  source should have its gold patch scored as a scorer self-test before use.

- Another important audit thread asked whether the scaffold, not just the model,
  was depressing solve rates. This found a major serving-path bug: the shim’s
  decode loop was hardcoded to argmax, so the configured agent temperature never
  actually reached generation. Claude framed the consequence carefully: all
  prior agent solve rates are lower bounds measured on a possibly handicapped
  model, though arm-to-arm comparisons remain internally valid because the
  handicap was symmetric. This became incidents 21/21b and a new rule that
  serving must follow the model card unless a deviation is explicit;
  accepted-but-ignored parameters are forbidden.

- Related scaffold discussion: the custom inference stack is estimated to cost
  roughly 3–10x wall-clock versus mature servers like vLLM/SGLang. The value of
  the custom stack is that it permits KV/value-state surgery and arm-symmetric
  serving; the cost is reliability and engineering overhead. Two future paths
  were captured: a hard path (eventual vLLM KV-connector/plugin integration for
  serving-layer deployment) and a nearer-term path (speeding up the current
  stack with flash attention, compiled decode, async serving, and validated
  incremental cache reuse). Neither was treated as immediate.

- A GLM fallback/swap ladder was explored. Claude’s view: first choice remains
  Qwen3-Coder-30B because it is same-family and near-drop-in; GLM-4.5-Air is the
  strongest “different blood, still affordable” fallback before jumping to very
  large models. For GLM specifically, template/tokenizer-level scaffolding
  validation passed locally using the generic prefix-stable path, but the
  small-model serving smoke was not completed cleanly because of an OOM; the
  honest remaining gate was a representative smoke of GLM-4.5-Air itself on
  rented hardware. The user also pre-authorized, conditionally, a tightly
  supervised capped-cost GLM trial if the current model continued to fail.

- The project then pivoted away from abandoned SWE rows entirely. Claude had
  briefly kept them running as “boundary documentation,” but the user disagreed
  that this was worth spending on a closed question; remaining SWE rows were
  purged. The active program became chain/exercise-style tasks on solvable
  ground, with validated instances auto-feeding priority lanes for full arm
  comparisons.

- Vendor benchmark tables became a major planning input late in the shard. The
  new rule was that the model card should be treated as a difficulty certificate
  before choosing evaluation tasks. This retrospective realization mattered
  because it aligned with the empirical boundary they had painfully discovered:
  repo-fixing was too hard for the subject model, while exercise-scale tasks
  were more plausible. A benchmark scouting pass found tau2-bench especially
  interesting: `banking_knowledge` appears to place policy in evictable
  conversation turns, while classic TAU domains keep policy in the system
  message. That implies a built-in causal dissociation for future confirm-phase
  work: compaction effects should appear where policy is evictable and not where
  it is safely retained. This was recorded as the planned standard-benchmark
  backbone, gated by a small pilot.

- By the end of the shard, the reported state was that several chain tasks had
  validated (4 of 6 in one update), constrained-arm rows were feeding the
  priority lanes, budget runway was getting tight, and the remaining spend was
  explicitly justified only by the prospect of producing a clean chain-tier arm
  table that could earn further budget.

Terminology / conceptual clarifications from `gpt-5.5` (Codex) prior-art and
method thread:

- Codex’s review of open-source/academic prior art concluded that public work
  overlaps strongly with the broad space but does not publicly duplicate this
  exact mechanism. The strongest mechanistic neighbor was “Models Take Notes at
  Prefill”; other relevant adjacent papers concern KV compaction/reuse or better
  text compaction, not specifically ValueGraft across a summary boundary. Codex
  thought public provider APIs strongly suggest frontier labs are working in
  this general area internally, but there is no public evidence they are doing
  this exact KV/value-state intervention.

- Codex helped refine the project’s own description: the intervention should be
  described as preserving/blending cached value vectors written during the
  full-context or summary-generation run, then inserting those values into the
  clean compacted-context cache while usually keeping keys fresh. “Attention
  values” is too ambiguous; “cached value tensors,” “write-time value state,” or
  “KV-cache value vectors” is better. Codex also emphasized that current
  validated variants are simple global alpha or low-DOF layer gating, not a
  fully tuned per-head coefficient matrix.

Codex paper-synthesis thread:

- Later, on a separate refresh, the user asked Codex to produce a serious
  paper-style “if we got cut off now, what can we conclude?” draft in an
  isolated working directory so it would not interfere with ongoing experimental
  work. Codex explicitly created a derived-analysis-only workspace, committed
  only files inside it, built an evidence ledger plus a draft paper, then
  revised it as the repo advanced. Notable update during this drafting pass: a
  larger Stage-1 LongMemEval aggregate (n=320) changed the standard-benchmark
  framing to “damage is confirmed but mitigation is bounded/flat in QA framing,”
  strengthening the caution against overstating the standard-benchmark evidence.

- The user then tightened git hygiene for Codex: avoid staging except
  immediately before commit, and prefer path-limited commits / explicit adds to
  minimize any risk of touching unrelated files in a live multi-agent repo.

Handoff-relevant themes:

- This shard is where the experiment’s task-selection policy becomes much
  stricter and more coherent: validate capability first, then spend on
  compaction comparisons, and use vendor/model-card benchmark guidance upfront.
- Several major negative/scoping findings were treated as real results, not
  hidden failures: repo-scale SWE tasks were too hard for this subject model in
  the tested setup; prior solve-rate measurements may be depressed by scaffold
  bugs; the custom server buys mechanism access at major reliability/performance
  cost.
- The confirm-phase direction emerging here is chain-tier solvable tasks plus
  TAU-style certified-difficulty benchmarks with evictable-policy structure,
  rather than continuing to push on abandoned SWE rows.
